# AI Agents Framework Overview

# Исследование: агенты на разных языках и экосистемах

## Зачем

Сейчас LLM-агентов всё чаще встраивают в реальные рабочие процессы: engineering support, внутренние ассистенты, автоматизация операций, поиск по документации, работа с задачами и инцидентами.

В больших компаниях возникает практический вопрос: **на чём писать таких агентов и на какой инфраструктуре их строить**. Часто есть уже сложившиеся команды и экосистемы: Python, Java/Spring, TypeScript/Node.js. При этом вокруг них есть стереотипы:

- Python — «самый ходовой» для LLM/AI, но его считают медленным или менее enterprise-friendly.
- Java/Spring — привычна большим компаниям, но кажется менее гибкой для agentic workflows.
- TypeScript — удобен для web/product-команд и streaming UI, но не всегда очевидно, насколько он хорош как agent runtime.

Цель исследования — не найти «лучший язык вообще», а понять, **какая экосистема лучше подходит для production-like LLM-агентов в разных организационных контекстах**.

## Основная идея

Сделать сравнительный анализ нескольких реализаций **одного и того же агента** на разных языках/фреймворках.

| Язык | Библиотека / фреймворк |
| --- | --- |
| Python | LangChain v1 |
| Java | Spring AI |
| TypeScript | LangChain JS v1 / Vercel AI SDK как optional alternative |

Все реализации должны иметь:

- одинаковый внешний HTTP API, желательно в стиле [Agent Protocol](https://github.com/langchain-ai/agent-protocol);
- один и тот же сценарий использования;
- один и тот же набор инструментов;
- сопоставимую работу с памятью;
- одинаковые критерии оценки.

Agent Protocol стоит использовать как тонкий внешний контракт, а не как центральную тему исследования.

## Сценарий агента

Предлагаемый сценарий: **engineering support agent для внутренней команды**.

Агент помогает разработчику разобраться с проблемой в сервисе, использует внутреннюю документацию, историю инцидентов, инструменты и память.

Пример сценария:

1. Пользователь сообщает: «После деплоя падает `billing-api`, посмотри runbook и предложи шаги».
2. Агент ищет релевантную документацию.
3. Агент читает runbook.
4. Агент смотрит последние похожие инциденты.
5. Агент задаёт уточняющий вопрос.
6. Агент предлагает план диагностики.
7. Агент создаёт задачу или incident ticket через tool.
8. Агент сохраняет полезную долгосрочную память, например предпочтения пользователя или факт о сервисе.
9. В следующем треде агент использует сохранённую память.

Такой сценарий покрывает основные возможности, важные для production-like агентов:

- tool calling;
- MCP-интеграцию;
- краткосрочную память: история сообщений, треды, continuation;
- минимальную долгосрочную память;
- side effects через tools;
- structured output;
- обработку ошибок;
- streaming / async execution, если фреймворк это удобно поддерживает.

## Инструменты и MCP

Стоит сделать один общий MCP server и подключить его ко всем реализациям.

Минимальный набор tools:

- `search_docs(query)` — поиск по внутренней документации;
- `read_doc(id)` — чтение найденного документа;
- `get_recent_incidents(service)` — получение похожих инцидентов;
- `create_task(title, description, metadata)` — создание задачи или incident ticket;
- `save_memory(fact)` — сохранение долгосрочной памяти;
- `search_memory(query)` — поиск по долгосрочной памяти.

MCP не должен становиться отдельным большим исследованием. Он нужен как общий способ дать агентам одинаковые инструменты и сравнить удобство интеграции.

## Память

### Обязательно: краткосрочная память

Нужно сравнить, как в каждой экосистеме реализуются:

- история сообщений;
- треды / conversation id;
- продолжение диалога;
- trimming или summarization контекста;
- persistence состояния между запросами.

### Желательно, но ограниченно: долгосрочная память

Долгосрочную память стоит сделать минимально:

- простое хранилище фактов;
- embeddings или простой поиск, если embeddings не успевают попасть в scope;
- tools `save_memory` и `search_memory`.

Не нужно глубоко исследовать memory architectures — это отдельная тема.

## Критерии сравнения

Сравнивать стоит не «скорость языка», а инженерную применимость.

Критерии:

- скорость разработки первой рабочей версии;
- количество glue code;
- удобство tool calling;
- удобство MCP-интеграции;
- работа с краткосрочной и долгосрочной памятью;
- streaming и async execution;
- retries, timeouts, error handling;
- structured output;
- observability: tracing, logging, debuggability;
- тестируемость;
- deployment complexity;
- удобство для enterprise-команд;
- зрелость документации и community;
- субъективный developer experience.

Отдельно стоит зафиксировать, где стереотипы подтверждаются, а где нет. Например, «Python медленный» может оказаться несущественным для LLM-агентов, потому что основная latency сидит в LLM calls, network I/O, tools и rate limits.

## Что не входит в scope

Чтобы уложиться примерно в 3 недели, не стоит делать:

- полноценный benchmark производительности языков;
- сложную multi-agent архитектуру;
- browser automation;
- глубокую RAG-систему;
- production Kubernetes deployment для всех реализаций;
- сложную долгосрочную память;
- сравнение всех существующих agent frameworks.

## Ожидаемый результат

К концу исследования должен получиться:

1. Небольшой репозиторий с тремя реализациями одного агента:
   - Python / LangChain v1;
   - Java / Spring AI;
   - TypeScript / LangChain JS v1, возможно с заметками по Vercel AI SDK.
2. Общий MCP server с одинаковым набором tools.
3. Единый внешний API в стиле Agent Protocol.
4. Один воспроизводимый сценарий проверки.
5. Таблица сравнения по инженерным критериям.
6. Короткий вывод:
   - когда лучше выбирать Python;
   - когда Java/Spring;
   - когда TypeScript;
   - какие trade-offs реальные, а какие являются стереотипами.

Практический ожидаемый результат — не универсальный рейтинг языков, а **decision framework** для выбора стека под agentic applications в конкретной компании.

## Предварительная гипотеза

- Python, скорее всего, окажется самым быстрым для прототипирования и наиболее богатым по AI/LLM-экосистеме.
- Java/Spring может оказаться лучшим выбором для компаний, где важны enterprise-интеграции, существующая Spring-инфраструктура, security, observability и поддержка командой backend-разработчиков.
- TypeScript может быть наиболее удобен там, где агент тесно связан с web-продуктом, streaming UI, full-stack разработкой и быстрыми product iterations.

Главный вопрос исследования: **какая цена у каждого выбора при переходе от прототипа к production-like агенту**.
